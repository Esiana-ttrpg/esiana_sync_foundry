# Wiki synchronization API limits

The Foundry module uses the campaign wiki tree and page detail APIs. The Import Content setting selects either the API user's accessible content or Esiana's Party projection (`previewAsPlayer=true`). Each import uses one normal Journal page. The module only grants player access when it can confirm that the imported representation matches the Party projection; otherwise it keeps the entry restricted. Esiana currently applies Party preview for campaign members, so the module cannot certify that projection for nonmembers.

The normal page creation endpoint accepts a page and its initial blocks. The page metadata endpoint changes title, parent and tags. The layout endpoint accepts the complete block array and replaces the layout. The entity/character-page block endpoints replace blocks on a character tab; they are not a general-purpose wiki block patch API. None of these wiki mutation paths accepts an expected page revision or an `If-Match` precondition. Reading a layout, modifying one block and submitting it therefore has a race with another editor, even when the client retains every unchanged block.

The plugin content-sync mutation does check `baseRevision` atomically against the page's `updatedAt`. However, its wiki `body` write replaces all wiki blocks with one newly generated text block. Its read representation flattens text blocks and omits non-text structure and per-block audience. The revision check alone therefore cannot make that mutation a safe round trip for structured or mixed-audience pages. The Foundry module refuses these body writes instead of silently discarding data.

A small general-purpose improvement would be a campaign-scoped wiki layout or block mutation accepting an expected page revision and applying the write atomically only if the revision still matches. It should return a conflict and the current revision when another editor wins. A targeted block mutation should retain every unrelated block and its visibility, ordering and identity. This would benefit external editors, automation and other third-party integrations that update wiki content concurrently; it does not require a Foundry-specific endpoint. The API must continue to enforce campaign and page authorization and validate referenced assets.

A separate core branch implements a revision-required layout endpoint. Until it is deployed, an Esiana-to-Foundry import can be refreshed without writing to Esiana. Foundry-to-Esiana and bidirectional wiki synchronization cannot safely preserve arbitrary structured pages under concurrent editing. Character tab blocks, rich widgets, asset copying, cross-page references and automatic permission transitions still require additional integration work and verification.
